# 学习路径与设计取舍

## DAG 为什么要先校验

需要同时验证图结构和数据引用。图无环并不代表引用合法：节点如果引用一个没有依赖关系的节点，未来并行执行时就存在竞态。因此引用目标必须是祖先，而不仅仅是“文件里出现过”。

离线示例故意将 summary 放在 greeting 前面。改变定义顺序，再查看实际执行轨迹，可以确认服务确实依赖图结构调度。

## 为什么先检查输入

如果先执行 HTTP，再在后面节点发现输入缺失，就已产生不可撤销的外部副作用。输入预检必须在首次请求前完成。测试使用本地 HTTP 请求计数验证这一点。

## 网络、状态与事务

网络操作可能很慢，也可能失败。执行时不长时间持有数据库事务；最终将运行结果整体保存。首版是同步运行，不承诺进程被强制终止时能恢复正在进行的节点。

SUCCEEDED、FAILED、SKIPPED 是不同业务状态。失败运行不是“没有记录”，HTTP 200 返回一份 status=FAILED 的记录，客户端要检查业务状态。

## HTTP 超时的范围

连接完成、收到响应头和读完整个正文是不同阶段。只设置请求头等待超时不足以防止正文悬挂，因此需要完整响应期限和取消操作。正文大小上限则避免一个节点无限占用内存。

## 下一次可以自己完成的实验

1. 为独立就绪节点加入并行执行，验证祖先引用、状态聚合和失败取消。
2. 在不改变现有语义的基础上加入条件分支，明确未选中节点的状态。
3. 为外部操作增加幂等键，再设计重试，解释哪些 POST 不能安全重放。

每项扩展都先写能观察行为的测试，再记录实现及取舍。不要把路线图写成已有能力。
